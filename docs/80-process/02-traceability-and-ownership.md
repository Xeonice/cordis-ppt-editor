「新增功能时同时更新产品、设计、前端、后端、测试文档」靠两件事保证：**需求编号贯穿五条线**，让「有没有更新到」可以机械判定（§1）；**每类事实只有一个归属文档**，让「更新到哪里」只有一个答案（§2）。变更里的文档影响矩阵（§4）是这两件事在单个变更上的体现。

## 1. 需求编号是主键

### 1.1 编号与 PRD 解析

需求编号只在 PRD 定义：PRD 03 九个功能域（`OF`、`ED`、`CO`、`PS`、`EM`、`SV`、`ML`、`AS`、`PM`）加 PRD 04 的 `NF`，形如 `ED-05`、`ED-15a`；每条带优先级与目标里程碑（PRD 05 M0 验收 3）。编号只追加不复用，删除的需求在 PRD 中标注「已删除」并保留编号。

G3、G4、G5 按下列规则读 PRD。规则只在共享模块 `docs/_tools/prdlib.py` 里实现一份，三个脚本共用；改规则先改本节，再改代码。

1. **正文**：换行认 LF、CRLF 与单独的 CR，文件开头的 BOM 去掉。去掉下面三类内容后余下的行是正文，行号不变：
   - 围栏代码块：以三个以上反引号或波浪线开头；闭合行用同一字符、不短于开头、其后只有空白；在引用块里开头的围栏，引用块结束时随之结束。
   - HTML 注释：行首（至多 3 个空格）的 `<!--` 起，到含 `-->` 的行为止，`-->` 之后的文字保留。行中的 `<!-- … -->` 是行内注释，可以跨行，但只在同一段落内：遇到空行、引用层级变化、标题、列表项、表格行、分隔线或 setext 下划线即止，标题行与表格行里的只能在本行闭合，没闭合的按字面保留；行内代码里的 `<!--` 不算。
   - `> 状态：` 状态头行。
2. **来源与编号**：PRD 03 是 `10-prd/03-features/*.md`，任一文件可定义九个功能域中的任一个；PRD 04 是 `10-prd/04-non-functional-requirements.md`，只定义 `NF`。编号形如 `[A-Z]{2,3}-[0-9]{2}[a-z]?`，字母、数字只认半角，其后不能紧跟 ASCII 字母或数字。
3. **定义行**只有两种：
   - 标题行：`#` 顶格的二级或三级标题，`##` 或 `###` 后隔空格（或制表符）紧接编号，如 `### ED-05 <标题>`、`## NF-01 <标题>`。一级标题与四级及更深的标题不算。
   - 表格行：以 `|` 开头（前面可有空白），首格是编号（可带 `*` 与反引号），且同时满足：① 功能域是本文件以标题行定义过的功能域（本文件没有标题行定义时不限）；② 首格里编号之后不紧跟区间或列表符（– — ~ … 至 到 、 ， / ； 与 和 及 或 等），也没有第二个编号；③ 该编号没有在 PRD 任何地方以标题行定义过。
4. **引用行**：首格以功能域编号开头、却不满足第 3 条的表格行（区间、跨域接口表、需求汇总表），以及首格以功能域编号开头、但不以 `|` 开头的 GFM 表格行。引用行不属于任何需求块，也不属于它所在的标题需求块。行里写了需求字段即报格式错误，这些字段不归入任何需求：严格写法的优先级、目标里程碑或落点豁免出现在行内任意处，或单元格以这三个标签开头（写法不合规也算；「粘贴优先级：」这类措辞不算）。
5. **需求块**：从定义行起，到下一个定义行或级别更高（`#` 更少）的标题之前。`### ED-01` 的块越过 `### 验收` 这类同级或更深的小标题，止于 `## 4. …`；PRD 04 `## NF-01` 的块含其下 `###` 小节，止于下一个 `NF` 或一级标题；表格行定义的需求遇到任何标题即止。
6. **优先级与目标里程碑**：取块内首个 `优先级：P0|P1|P2` 与首个 `目标里程碑：M<n>`（`<n>` 后可带 `+`，如 `M4+`；`M2（内部）/ M4（公开）` 记 M2）。冒号为全角，冒号后可有空白，可写在行内任意处；标题行里写的不算，表格行定义的需求取该行编号之后的单元格。PRD 03 的需求（已删除的除外）缺任一项、同一块内同一字段多于一处，都是格式错误；PRD 04 的 `NF` 不写，记为无优先级。
7. **落点豁免**：块内单独成行写 `- 落点豁免：<线>——<理由>`，定义行本身不算。行首可有空白，`-` 后至少一个空格（或制表符），冒号为全角，冒号与线名之间、线名与破折号 `——` 之间不留空格；线取 设计 / 前端 / 后端 / 前后端 / 测试。理由去掉空白与零宽、软连字符等格式字符后不能为空，也不能是 `<理由>` 这类模板占位或「无」「-」「待定」「TBD」「N/A」一类占位值。同一条线写了多条时取第一条。
8. **已删除**：标题末尾带括注「（已删除）」或「（已删除，<说明>）」（全角或半角括号；说明前可用 ，,；;：: 或「空格 + 日期」，不认「、」），且块内没有优先级。块内仍写了优先级时报格式错误，按未删除的需求处理。
9. **重复定义**：同一编号以首次定义为准，后面的同号块整块不算，报格式错误。

**格式错误**只把静默失效变成报错，不改变上面解析出的结果。G4 全部报出并判失败；G3、G5 只用解析结果，不重复报格式错误：G3 只报读不了或不是 UTF-8 的 PRD，G5 按 3.1 的读取问题报（PRD 文件也是它的来源文件）。格式错误包括：

- 来源：PRD 03 目录或 PRD 04 缺失；PRD 03 整体或某个 PRD 文件没有解析到任何需求；文件读不了、不是 UTF-8（报首个坏字节所在行，按替换字符继续）；围栏或注释直到文件尾都没闭合（其后的内容都不解析）。
- 定义：像需求定义却不合格式的标题或表格首格，即级别、缩进、加粗、全角、数字位数不对，前面加了「新增：」一类标签，功能域不属于本文件，或写成 setext 标题。
- 字段：像优先级、目标里程碑或落点豁免却写错的行，即行首或单元格开头以该标签开头，但用了半角冒号、冒号前留空格、加粗、反引号、全角字母数字或取值越界；落点豁免另含写在引用块里、用别的列表符、`-` 后无空格、线名或破折号写错、理由为空或占位。
- 位置：不在任何需求块内的这三种字段；引用行里的字段（第 4 条）；表格定义行单元格里的落点豁免（不算豁免，需要豁免时改用标题行定义）。
- 第 6、8、9 条所列的情形。

### 1.2 各线的落点与引用识别

| 线 | 怎么算「有落点」 | 说明 |
|---|---|---|
| 设计 `20-design` | 设计文档引用了该编号（界面文档写「需求：ED-05、ED-06」，或在相关段落引用） | 不扫 `20-design/` 顶层的 `playground/`、`mockups/`、`prototype/` |
| 前端 `50-frontend` | 前端文档引用了该编号 | 能力表 50/18 把需求细分为能力 id，引用能力 id 不替代引用需求编号（下文第 5 条） |
| 后端 `60-backend` | 后端文档引用了该编号 | 同上 |
| 测试 `70-testing` | 测试文档引用了该编号，且代码中有带 `@req PRD:<编号>` 的测试 | 代码侧规则（R1–R11）沿用 [70/13](../70-testing/13-requirements-traceability.md)，本线不重复定义 |

G4 只扫各线目录下的 `.md`，按读者看得见的文字数引用：正文与围栏代码块里的都算（mermaid 节点、代码示例里的 `@req` 标签都看得见），HTML 注释与 `> 状态：` 状态头行里的不算。只计 PRD 中存在、且按下列规则识别为需求引用的编号。各线文档读不了、不是 UTF-8，或 HTML 注释直到文件尾都没闭合时报错；围栏没闭合不丢引用，不报。

**需求编号引用识别**（G4 数落点、G5 反查共用，在 prdlib 实现）：

1. 文本中独立出现的编号算：前后不是 ASCII 字母或数字，所以 `PRD:ED-05`、`PRD ED-05`、「（ED-05）」都能识别。识别时不看编号是否存在：G4 只计 PRD 中有的编号，G5 对没有的报失配（§3.2）。
2. `CO` 前缀与 rulings §4.18 的条目编号同形，须带 PRD 字样才算需求引用。带 PRD 字样有三种认法：编号前 15 个字符内有「PRD」；编号是指向 `10-prd/` 的链接文字（`[CO-15](../10-prd/…)`），或紧跟在指向 `10-prd/` 的路径、链接之后；编号是列表续项，即与前一个编号之间只隔列表或区间符（、 , ， / ~ – — … 至 到 与 和 及 或，可带空白、`*` 与反引号），沿用前一个编号的判定。不带 PRD 字样的 `CO` 编号不算，G4 在缺口原因里提示改写为「PRD CO-xx」。
3. `CO` 编号前 15 个字符内有「§4.18」「4.18/」或「rulings」时，是 rulings §4.18 的条目，不算需求引用，带 PRD 字样也一样；列表续项沿用前一个编号的这一判定。
4. 证据条目不算：写在「证据」之后的编号链（编号以列表或区间符分隔）里、且属于证据清单（`docs/_evidence/` 与 `docs/*/_evidence/` 下 `*.json` 的 `"id"`）的编号。不在清单里的照常算。
5. 能力 id 不算：GFM 表格里表头为「能力 id」的列，以及表头以「id | 能力」开头的表的首列（含表格内不带竖线的续行）。其余列（「需求 id」「ID」「用例 id」等）照常算。
6. G3 识别 proposal「## 需求编号」里的编号时只用第 1、3 条：该节的编号按模板都是 PRD 编号，所以不带 PRD 字样的 `CO` 也算，第 4、5 条不适用；只认十个功能域。

### 1.3 覆盖规则（G4）

- 每条 **P0、P1** 需求：设计 ≥ 1 处；前端与后端合计 ≥ 1 处；测试文档 ≥ 1 处。缺口以「需求编号 × 线」为单位，线取 设计 / 前后端 / 测试。
- 某条线确实不涉及时，在 PRD 该需求下写一行 `- 落点豁免：<线>——<理由>`（如 `- 落点豁免：设计——纯服务端能力，无界面`，格式见 §1.1 第 7 条），G4 据此跳过该线；豁免理由不能为空。「前后端」豁免抵前端与后端合计这一项；只写「前端」或只写「后端」不抵，两条都写才抵。
- **P2** 与无优先级的需求（PRD 04 的 `NF`；优先级没写对的 PRD 03 需求另报格式错误）只出现在覆盖报告中，不判失败；已删除的需求不检查。
- **棘轮**：`dev-process` 归档时生成基线 `docs/_tools/req-coverage-baseline.json`（当时已有的缺口）；此后新增缺口即失败，基线只能减少，由 `docs-coverage-baseline` 变更清零。基线里已经消失的缺口同样判失败，须运行 `--write-baseline` 收紧并随同一提交入库。PRD、各线文档或证据清单有解析错误（§1.1 的格式错误、§1.2 的读取问题）时，算出的缺口不可信，`--write-baseline` 拒写并以退出码 1 结束。

## 2. 一个事实一个归属

非归属文档只写编号、键或链接，不复述定义；确需摘要时注明「以 <归属文档> 为准」。归属变更（把某类事实挪到别的文档）本身是 L2 变更。

| 事实 | 唯一归属 | 键 |
|---|---|---|
| 需求、验收标准、优先级、里程碑 | `10-prd/03-features/*`、`04`、`05` | 需求编号 |
| 产品指标 | `10-prd/06` | 指标 id |
| 界面布局、交互、状态、文案 | `20-design/03-screens/*` 与 playground 对应路由 | 界面号 `03-NN` |
| 设计 token 的取值 | playground `src/index.css`（代码即源）；`20-design/04` 只展示与解释 | token 名 |
| 跨端命令与错误码 | `30-architecture/05`（命令）、`30-architecture/10`（错误码与观测命名） | 命令 id、错误码 |
| 协同协议消息与关闭码 | `30-architecture/06`；服务端挂点见 `60-backend/16` | 消息类型、关闭码 |
| 架构决策 | `30-architecture/adr/*` | ADR 号 |
| npm 包 | 章程 §5.2 | 包名 |
| cordis 插件、贡献点、preset 装配 | `40-modules/16` | 插件 id、贡献点 id |
| 文件结构（每个源文件，含测试文件） | 40-modules 各模块的 §4 目录树与 §5 文件表（rulings §4.25 DP-5、DP-8） | 文件路径 |
| 浏览器侧行为、状态、路由、事件 | `50-frontend/*`（事件见 50/15） | 路由、事件名 |
| REST 路由 | `60-backend/15` | 方法 + 路径 |
| 表、列、约束、迁移 | `60-backend/09`–`13`（迁移编号见 60/08 §10.1） | 表名、迁移号 |
| 配置键 | `60-backend/17` | 配置键 |
| 队列与作业 | `60-backend/06` | 队列名 |
| 测试用例、CI 步骤、PRD 检查名 | `70-testing/*`（步骤见 70/12，检查名见 70/13） | 用例号、步骤名、检查名 |
| 裁决 | `00-charter/rulings-2026-09-14.md` | `§4.N` 与条目 id |
| 术语与已裁定更名 | 章程 §4；`docs/_tools/terms.json` | 术语 |

## 3. 文档间引用反查（G5）

文档里引用了归属在别处的键时，键必须在归属文档中存在。首批检查以下六类（键的形式明确、误报少），判定细则见 3.1–3.5。实现是 `docs/_tools/check-doc-refs.py`，需求编号的识别与 PRD 清单调用 prdlib，与 G4 同一份代码。

| 类别 | 引用形式 | 必须存在于 |
|---|---|---|
| 需求编号 | 按 §1.2 识别为需求引用、前缀是十个功能域之一的编号：`PRD:ED-05`、`PRD ED-05` 或裸编号（`CO` 前缀必须带 PRD 字样，避免与 rulings §4.18 的 `CO-xx` 混淆） | PRD 需求清单（§1.1） |
| REST 路由 | 反引号中的 `GET /…`、`POST /…` 等 | `60-backend/15` 路由表 |
| 错误码 | 反引号中首段是错误码命名空间的点分小写 token，如 `server.plugins.conflict`（哪些算引用见 3.4） | `30-architecture/10` |
| 界面 | `03-screens/NN`、「设计 03-NN」 | `20-design/03-screens/NN-*.md` |
| ADR | `ADR-00NN` | `30-architecture/adr/00NN-*.md` |
| 裁决小节 | `rulings §4.N` | rulings 中的 `## 4.N` 标题 |

事件名、配置键、队列名、插件 id 作为第二批，在 `docs-coverage-baseline` 归档后加入。

### 3.1 扫描范围与豁免

- **来源**：`docs/` 下全部 `.md`。跳过 `00-charter/rulings-*`（裁决原文）、`_evidence/` 与 `00-charter/_evidence/`，以及任意层级名为 `playground`、`mockups`、`prototype`、`node_modules`、`dist`、`docs-site` 或以点开头的目录；`30-architecture/adr/` 照查。只查给出的文件时，`docs/` 里的文件同样适用这些路径豁免。
- **只查正文**（§1.1 第 1 条：围栏代码块、HTML 注释与 `> 状态：` 头行不查）。REST 路由与错误码只认行内代码（反引号片段）里的写法；需求编号、界面、ADR、裁决小节在整行里识别。
- **历史陈述行整行不查、不计数**：豁免沿用 `check-terms.py` 的口径，行内出现其历史陈述标记「原名」「原称」「原：」「弃」「作废」「取代」「替换」「→ 2026-」「旧名」之一即算，按子串匹配，表格行同样整行豁免。词表与 `check-terms.py` 逐字相同，不增不减，也不按片段或单元格细分。
- **归属文档自己的登记不算引用**：60/15「已删除端点」表的行与「仍未排期的端点」段落，以及 60/15 别处提到的、它自己登记为已删除或未排期的端点；30/10 里提到的、它自己声明为已废弃的码。别的文档再出现这些键照常按失配报出，除非该行是历史陈述行。
- **读取问题判失败**：来源文件或归属文档不是 UTF-8（按替换字符继续检查，报首个坏字节所在行）；围栏或注释直到文件尾都没闭合（报起始行，其后不查）；来源文件读不了（报第 1 行）；证据清单读不了或不是 UTF-8。PRD 文件也是来源文件，同样按这几条报；PRD 的格式错误由 G4 报，G5 不重复。

### 3.2 需求编号、界面、ADR、裁决小节

### 3.3 REST 路由

- **引用**：行内代码里的「方法 路径」。方法为 GET、POST、PUT、PATCH、DELETE，可用 / | 、 , ， 并列，拆成多处；路径以 `/` 或 `…/` 开头，遇到空白、反引号或中文标点（、，。；：（）「」【】）即止。没有字母的路径（如 `GET /…`）不算引用。
- **归一**：去掉 `/api/v1` 前缀、查询串与末尾斜杠；`:param`、`{param}`、`<param>` 统一为占位；段内「a|b」「{a|b}」展开为多条；紧贴路径（不在段首）或隔空白跟在路径之后的「{…}」是请求体提示，不参与路由匹配；末尾的「*」是前缀通配，有该方法的路由以这些段开头即可。
- **归属**：60/15 中表头含「方法」「路径」两列的全部表格；路径格里写了「name ∈ a | b」的占位段只认这些取值。
- **逐段比对**：引用的占位段只配路由的占位段。引用的字面段配路由的同名字面段，或填进路由的占位段：带取值的占位只收取值；其余占位只收示例值，即不像路由字面段（小写字母开头、只含小写字母、数字与连字符）的值，以及 UUID 和 ≥ 8 位、兼有数字与字母的十六进制串；与某个路由字面段只差大小写的值不收。所以「/documents/serch」不会被「/documents/:id」吸收。以「…/」开头的省略写法从路由的某一段起对齐：首段须对上同名字面段（或占位对占位），窗口之后只允许剩占位段。
- **已删除与未排期**：60/15「已删除端点」表（首列表头「端点」）里的端点，别处引用按失配报出并注明替代；「仍未排期的端点」段落里的端点，别处引用按失配报出并注明尚未进路由表。这两类登记带请求体提示时，同方法、同路径且提示里有同名字段的引用照样按已删除或未排期报出，即使去掉提示后与活路由同名；不带提示的同路径引用按活路由判定。

### 3.4 错误码

**登记**（取自 30/10）：

- 码：30/10 §1.1a「域 | 码」登记表按域 × 码展开；其他表里表头以「码」「错误码」开头或为「定稿」的列中的码，紧跟在「原 / 原名 / 原称 / 旧 / 废 / 弃」之后的旧码不算，「*.名」只对同一单元格列出的域展开；TS 围栏里 `'x.y':` 形式的声明键。
- 已登记域：登记表的域、已登记码的域，以及 30/10 §1.1 中以空格连写的域清单（≥ 3 个）。命名空间：已登记域的首段。
- 已废弃码：30/10 正文里紧挨废弃标记（「废弃」「作废」「弃用」「不再使用」「原」「旧」等，在码前或码后）的未登记码形 token（末段含下划线），以列表符连写的同组 token 一并算。
- 另有归属的同形键（§2）：40-modules/16 的贡献点 id、60-backend/07 的审计 action、50-frontend/15 与 60-backend/18 的 span 名（及 30/10 §3.2 列出的 span 名）、60-backend/17 的配置键、30-architecture/05 的命令与变更 id。

**候选 token**：行内代码里首段属于命名空间的点分小写 token，各段以小写字母开头、只含小写字母、数字与下划线，含通配「x.*」「x.y.*」；前后紧贴其他标识符字符的、其后紧跟「(」「=」的、紧贴冒号再接非空白的（如「slide.ui:zh-CN」）不算。末段是文件扩展名的是文件名（去掉末段后恰好是已登记两段域的除外，如「format.pptx.lock」照样按码看），与已登记域同名的是域引用（如「server.documents」），这两类都不看。

**语境**（在同一单元格里判断，不在表格里时在同一行里判断）：

- 强语境，满足其一：
  - 片段所在列的表头含「码」（「编码」「代码」除外）或为「定稿」；
  - 片段前 12 个字符以内、不跨分句标点（，,；;。！？!?），以「…码」（同样除外编码、代码）、「错误域」或「错误域前缀」结尾，其后可带「为 / 是」、左括号、冒号或等号；
  - 片段内有错误用法：`errors.report(` 一类（report、create、raise、wrap）、`err(`、`code:`、`code=`、`Error<`、`?error=`、`&error=`、`error:`、`error=`；
  - 以列表符（、 / 或 与 和 及 , ，）与上一个强语境片段连写。
- 弱语境，强语境之外再满足其一：
  - 表头含「错误」「诊断」「点式值」；
  - 片段前（同上窗口）以下列词结尾，其后同样可带「为 / 是」、左括号、冒号或等号：错误类型、错误、诊断、抛、抛出、报、报错、拒绝、失败返回、失败时返回、失败为、失败时为、返回码、Result 为、reason、reason 为、error、error code、code（英文不分大小写），或 HTTP / WS 状态码（三位的 1xx–5xx、四位的 4xxx 与 10xx）；「上报」「汇报」「通报」「播报」「预报」「简报」「情报」「警报」「电报」里的「报」不算；
  - 片段后 12 个字符以内紧跟括注状态码（「（409）」）或「错误」「报错」；
  - 写成「以 `x` 失败」；
  - 片段所在分句（按「。；;」切）出现「错误码」或「诊断码」；
  - 以列表符与上一个弱语境片段连写。

**判定**（每个候选 token 取第一条成立的）：

- ① 已登记的码：有效。通配「p.*」须有已登记码以「p.」开头，只登记了域、没有码的前缀不算。
- ② 30/10 记为已废弃的码，以及前缀下只有已废弃码的通配：失配，注明已废弃，不看语境。
- ③ 不是错误码的同形键：另有归属的键；通配「p.*」中 p 是另有归属的键或其真前缀，或 p 的首段是已登记、但在 30/10 没有任何登记码的命名空间，且被另有归属的键用作首段（现为 command、layout、slide、store）；以及表头以「键」「键名」结尾的列里的 token（budgets.json 键、配置键）。只在强语境里按错误码核对，30/10 没有即失配并注明同形键的归属；不在强语境里时不看、不计数。
- ④ 其余通配一律核对，不看语境：没有已登记码以「p.」开头即失配，如「transport.*」「server.nonexist.*」。
- ⑤ 码形 token 一律核对，不看语境，未登记即失配：server 下的两段 token（server.<资源> 是域，资源未登记即失配，如「server.webhook」）与三段及以上 token；前两段是已登记两段域的三段 token（如「format.pptx.x」）；其余三段且末段含下划线的；两段且末段含下划线、或末段是已登记码用过的单词名（如 forbidden、conflict）、或与同域某个已登记码的相似度 ≥ 0.88（difflib，疑似拼错）的。
- ⑥ 其余非通配 token，即 server 之外两段且末段是普通单词、三段且末段无下划线、四段及以上的：只在弱语境里才算引用并核对。

**取舍**（2026-10-04 实现回写）：本节初稿只写「反引号中形如 `server.plugins.conflict` 的点分小写码」。只按命名空间过滤时，现有文档会多报约 200 处不是错误码的同形写法，多是命令、API、作业名、i18n 命名空间与 DOM 接口（如「document.title」「store.transact」「slide.crop」）。因此：已登记码、已废弃码、通配与码形 token 不看语境，前缀写错（「transport.*」）、server 域名笔误（「server.webhook」）与两段、三段里末段带下划线的码名必报；另有归属的同形键是别类事实（§2），只在强语境里按错误码核对；其余普通同形写法只在弱语境里核对。语境词表的增减同样先改本节，再改脚本。

### 3.5 棘轮

与 G4 相同，`dev-process` 归档时生成基线 `docs/_tools/doc-refs-baseline.json`（当时已有的失配）；此后新增失配即失败，基线只能减少，由 `docs-coverage-baseline` 清零。（2026-10-04 实现时补：现有文档已有失配，直接全量失败会阻断所有文档提交。）

- 基线以（文件, 类别, 引用）为键、记出现次数，不含行号。现有次数超过基线即「新增」，少于基线即「可收紧」，两者都判失败；收紧须运行 `--write-baseline`，随同一提交入库。
- 基线文件不存在时视为空；不是合法 JSON 或条目不合法时报「基线文件:行」并判失败，不带文件参数的 `--write-baseline` 可整体重写。
- 有读取问题（3.1）时 `--write-baseline` 拒写并以退出码 1 结束，因为此时的失配不可信。
- 只查给出的文件时，只比对这些文件的键，`--write-baseline` 也只替换这些文件的键；此时原基线不合法则拒写。

## 4. 文档影响矩阵

每个变更的 proposal 都有这张表，6 行逐行表态：

```markdown
## 文档影响矩阵

| 线 | 表态 | 说明 |
|---|---|---|
| 产品 | 需更新 | 新增 PM-17；PRD 05 M3 范围加一行 |
| 设计 | 需更新 | 03-09 增加「导出插件清单」状态 |
| 前端 | 需更新 | 50/03 §10 |
| 后端 | 不涉及：清单在浏览器内生成，不经服务端 | |
| 测试 | 需更新 | 70/06 e2e、70/13 §3 |
| 其他 | 不涉及：无章程、架构、模块、工具登记改动 | |
```

- **矩阵**只写在 proposal 的 `## 文档影响矩阵` 节内、恰好一张表，修订就地改表；节外标题含「文档影响矩阵」的节或节外表头含「线」「表态」列的表，G3 判格式错误，节外的矩阵不核对。
- **表态**只有两种：`需更新`，或 `不涉及：<理由>`（理由不能为空）。
- **需更新**的行，docs-sync 至少有一条该线目录下文件的回写记录，且这些文件在本变更的分支上确有改动（G3）。
- **回写记录**只写在 docs-sync 的 `## 回写记录` 节内，分轮追加的写进原节（在它的下一个二级标题之前另起一张表或用 `###` 小标题）。节外标题含「回写记录」的节（任意级别，如追加在文件末尾、落进 `## 偏差记录` 的 `### 回写记录（第二轮）`）或节外表头含「线」「文件」列的表，G3 判格式错误；其中的记录照样核对，也计入与其他进行中变更的重叠检查，不因写错位置而被忽略。
- **其他**一行覆盖 `00-charter`、`30-architecture`、`40-modules`、`80-process`、`docs/_tools`。
- **新增功能**（本变更在 PRD 新增需求编号）时：产品、测试必须「需更新」；设计必须「需更新」，除非新需求写了设计的落点豁免；前端、后端至少一行「需更新」。这些新编号同时进入 G4 的覆盖检查。
- **L1 变更**通常五线都写「不涉及」，「其他」行可能是 40-modules 的内部文件登记。
