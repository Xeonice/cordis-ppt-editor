# Proposal

级别：L2

## Why

仓库只有文档，即将开工 M0 收尾与 M1 实现。用户要求研发过程严格遵循文档设计，并在新增功能时同步更新产品、设计、前端、后端、测试文档。此前各轮回写靠 rulings 加多 agent 临时组织，2026-10-03 的对齐审计（rulings §4.24）仍查出 7 处跨线矛盾和一批缺口，说明需要固化流程，并用机械检查守住内容一致。

## What Changes

- 新建研发流程线 `docs/80-process/`：README（原则、总览、路线图、待决）、01 变更生命周期（三档、五步、设计质量门、偏差、分支提交、缺陷、评审、发布、断点续做）、02 追溯与归属（需求编号主键、覆盖规则、事实归属表、文档间引用反查、影响矩阵）、03 门禁（G1–G7）。
- OpenSpec 工作流 `openspec/schemas/cordex-docs-first/`（proposal → docs-sync → design → tasks，不含 specs）与 `openspec/config.yaml`。
- 仓库根 `CLAUDE.md`：给 agent 会话的流程摘要。
- 章程与裁决：rulings §4.25 记录用户裁决 DP-1…DP-7、DS-1，默认值 DS-2，以及随本变更评审确认的总编排提议 TP-1…TP-5；章程 §8 文档树、§9.1 分工、§9.2 第 9 条同步；`docs/README.md` 阅读顺序加入 80。
- 测试线登记：70/12 在 `scanners` job 下登记 `process-*` 与 `docs-*` 步骤及激活时间；70/13 说明文档侧覆盖（G4）与代码侧 R1–R11 的分工。
- PRD 05 M0 验收 4 补「研发流程门禁 G1–G7 就位」。
- 实现（评审通过后）：`docs/_tools/check-change-impact.py`（G1–G3）、`check-req-coverage.py`（G4，含基线）、`check-doc-refs.py`（G5）；文档站生成器加入 80 分区；`docs/_tools/README.md` 登记新脚本。G6 的两个脚本随 `m0-governance-gates` 实现。
