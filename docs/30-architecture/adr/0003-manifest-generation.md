# ADR-0003 Manifest：静态分析生成、入库、CI 与运行时三方一致性

> 状态：草稿 | 负责：架构-结构 | 更新：2026-09-14；2026-09-25（矛盾收口，rulings §4.18） | 依赖：charter v0.1；裁决 `docs/00-charter/rulings-2026-09-14.md` §4.18 GV-14/GV-15/GV-17

## 状态

提议。

## 背景

Univer 没有 manifest、清单或 schema，不运行系统无法知道插件贡献了什么（A9）；且「声明」与「实现」常常脱节（A16–A27）。章程要求 Manifest 由源码生成，不运行即可知道插件的 provides / injects / contributes / events / 同构类。

## 决策

三方一致性：**源码 → 生成物（入库）→ 运行时**，任一环节不一致即失败。

1. **生成器** `tooling/manifest-gen`（ts-morph；即 `tooling/scripts/scan-manifest.ts`，M-01 §12 D-1——两个名字指同一个脚本，2026-09-25 按 rulings §4.18 GV-17 注明，语义不改）读取每个插件包的 `src/plugin.ts`、`src/*.contribution.ts`、`src/services/**`、`apply` 可达的调用点，提取：
   - `name`、`inject`（字面量数组/对象键）、`provide`、`Config`（zod → JSON Schema）；
   - `ctx.contribute(<Ident>, …)`：`<Ident>` 解析到 `defineContributionPoint({ id })` 的 `id`；键在静态可知（字面量对象的 `id`/`type` 字段）时记录；
   - `defineContributionPoint({ id })` → `points`；
   - `ctx.on/once('lit')` → `listens`；`ctx.emit/parallel/serial/bail('lit')` → `emits`；`ctx.waterfall('lit')` → `waterfalls`；
   - `ctx.get('lit')` → `optional`；
   - `package.json`：`version`、`cordex.iso`、`peerDependencies` → `kernel`/`peers`；
   - `unitScoped`：`provide` 或 `inject` 含隔离服务名（`store/history/selection/render/presence` 或任一 `DocumentType.unitServices` 静态可知值）。
2. **生成物**：写入 `src/manifest.ts`（`export const manifest = {...} as const satisfies Manifest`，头部 `// generated by manifest-gen — do not edit`），构建时序列化为 `cordex-manifest.json` 随包发布（`cordex-manifest.json` 是构建产物、**不入库**；本条是章程 :87「由源码生成」与 §6.2 的落点，09-type-discipline 与 40-modules 中「`manifest.ts` 人工编写以获得意图声明」「`cordex-manifest.json` 入库」的写法以本条为准，rulings §4.18 GV-17）。
3. **入库与 CI**：`manifest.ts` 入库；CI `manifest-gen --check` 重新生成并要求无 diff（像 api-extractor 的 `.api.md`），使能力变更在 PR 中可见、可评审。
4. **不可静态判定**的情形（动态字符串、循环内 `contribute`、条件 `inject`）：生成器输出 `dynamic` 标记；`--check` 要求源码对应位置有 `/* cordex-manifest: dynamic <理由> */` 注释，否则失败。宁可要求作者显式承认，不做猜测。
5. **运行时校验**（kernel `manifest/verify.ts`）：插件 Fiber 首次 `ACTIVE` 后，比对实际：`provides`/`injects` 必须完全相等；`contributes` 的 point 集合相等，键集合 ⊇ 静态键集合；`listens`/`emits` 运行时 ⊇ 静态；`iso` 与当前环境不相容（dom 包在 Node）→ 失败。不一致 → `strictManifest` 时 Fiber `FAILED`，否则 `errors.report` + `kernel/manifest-mismatch`。CI 的插件测试以 `strictManifest: true` 运行。
6. **README 段落同步**：生成器把「服务/贡献点/事件」表写入各包 README 的标记区，避免文档与代码脱节。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
|---|---|
| 手写 `manifest.ts`（源），生成 JSON | 手写即会脱节（A9 的根因）；需要额外校验器比对源码，等于仍要写生成器 |
| 运行时反射生成（挂载后 dump） | 违背「不运行即可知道」；且 dom 包无法在 CI 的 Node 环境 dump |
| 仅 `package.json` 字段（`cordex.contributes` 数组，VS Code 风格） | VS Code 的 `contributes` 是纯声明且由宿主执行，我们的贡献由代码执行，声明与代码必然双份 → 用生成消除双份 |
| 装饰器/宏在源码中标注 | 与函数插件形态不合；仍需静态分析 |

## 后果

- 正：PR 中能力变更可见；运行时可诊断「声明了但没做」与「做了但没声明」；第三方插件审核有据（M4）；loader/UI 可读 `configSchema`。
- 负：生成器是需要维护的工具（对 ts-morph 与 TS 版本敏感）；作者需为动态注册加注释。

## 如何被机械验证

- scanners job 的 `scan-manifest --check` 步骤：从源码重新生成 `manifest.ts`，与入库文件比对无 diff（2026-09-25，rulings §4.18 GV-14：不新增 job 名，13 个 job 名封闭集合不变；原「CI job `manifest-check`」作废）。
- kernel `__tests__/manifest-verify.test.ts`：构造声明与实现不一致的插件 → strict 下 FAILED。
- 扫描器 `scan-manifest` 规则 (a)（TD-090）的存在性检查：`cordex.role ∈ {plugin, provider, definition}` 的包必须有 `src/manifest.ts` 且被 `index.ts` 导出（供运行时校验读取）；`library`/`app`/`tooling` 角色豁免（角色集合以 09-type-discipline/06 §6 规则 (a) 与 08 §11 为准；2026-09-25，rulings §4.18 GV-15：原名 `manifest-present` 并入 `scan-manifest`，对照见 09-type-discipline/08 §11）。
- 生成器自身有负向测试语料（动态键无注释 → 失败；语料目录随脚本落在 `tooling/scripts/__tests__/` 下，以 40-modules/01 为准，原写 `tooling/manifest-gen/__fixtures__/`）。
