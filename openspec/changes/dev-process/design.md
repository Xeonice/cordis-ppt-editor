# Design

## Context

流程与门禁的判定规则已在 docs/80-process/02、03 定稿（评审 2026-10-04 通过）。本设计只定 `docs/_tools` 下三个门禁脚本（及其共享模块 `prdlib.py`）与文档站改动的实现取舍；G6 的两个脚本随 `m0-governance-gates` 实现，不在本变更。实现中细化的口径（PRD 解析、需求编号引用识别、错误码的通配与语境、棘轮的拒写条件）已按 80/01 §5 回写 80/02 §1.1–§1.3、§3（2026-10-04），本文件只记实现取舍，不另立口径。

## Goals / Non-Goals

**Goals:**
- `check-change-impact.py`（G1–G3）、`check-req-coverage.py`（G4）、`check-doc-refs.py`（G5）可在本地与 CI 运行，失败报「文件:行 + 原因」，退出码 1。
- G4、G5 生成当前缺口的基线文件，按棘轮执行。
- 文档站加入 80-process 分区，决策面板纳入 rulings §4.25。

**Non-Goals:**
- 不接 CI（随 `m0-ci-workflows`）；不做 G6；不修补基线里的既有缺口（随 `docs-coverage-baseline`）。

## Decisions

1. **共享模块 `prdlib.py`，三个脚本共用**：仅用 Python 标准库（兼容 3.9），与现有 `docs/_tools` 一致，换机器零依赖。Markdown 正文切分、GFM 表格、PRD 需求清单与需求编号引用识别只在 `docs/_tools/prdlib.py` 实现一份；`check-change-impact.py`、`check-req-coverage.py`、`check-doc-refs.py` 都 `import prdlib`，各自先把脚本所在目录插入 `sys.path`，从别的目录运行或用 importlib 加载也找得到。一致性由同一份代码保证，另有两道核对：`python3 docs/_tools/prdlib.py` 运行内置自测；需求的机读形式统一由 `prdlib.req_json` 输出，`check-change-impact.py --list-reqs`、`check-req-coverage.py --json` 的 `requirements` 与 `check-doc-refs.py --registry` 的 `requirements.items` 可逐条比对。初版「每个脚本自包含、规则逐字相同、交叉测试保证」在实现中三份解析多次分叉（块终点、标题行优先级、「已删除」认法、CO 的认法各不相同），2026-10-04 改为共享模块。
2. **需求编号解析**：条文以 80/02 §1.1（PRD 解析）、§1.2（引用识别）为准，只在 `prdlib.py` 实现；改规则先改 80/02，再改 `prdlib.py` 与其自测。实现要点：定义行是 `#` 顶格的 `##` / `###` 标题紧接编号，或以 `|` 开头、首格是编号的表格行（另须本文件功能域、首格非区间或列表、该编号未以标题行定义，否则是引用行，写了需求字段即报错）；需求块止于下一个需求或级别更高的标题；优先级、目标里程碑取块内首个严格写法，标题行里的不算；落点豁免取块内单独成行的 `- 落点豁免：<线>——<理由>`，理由不能为空或占位；PRD 的格式错误只由 G4 报（退出码 1）；G3 只报读不了或不是 UTF-8 的 PRD，G5 只报读取问题（PRD 文件也是它的来源文件）。引用识别：`CO` 须带 PRD 字样（前 15 个字符内「PRD」、指向 10-prd 的链接文字或路径、列表续项），前 15 个字符内有 `§4.18`、`4.18/` 或「rulings」的不算；「证据」之后、属于证据清单的编号与能力 id 列里的编号不算；G4 另计各线文档围栏代码块里的编号，G5 只查正文；G3 读 proposal「## 需求编号」时只去掉 rulings §4.18 的条目。
3. **G1–G3 的变更 id 来源与 proposal、docs-sync 的解析**：依次取 `--change`、环境变量 `CORDEX_CHANGE`、PR 正文环境变量 `PR_BODY` 首行 `Change: <id>`、当前分支名 `change/<id>`。G1、G2 只在本分支改动触及代码路径（80/03 §2.1）时触发；G3 只要关联了变更就运行。docs-sync 写错位置的内容一律判格式错误、但不丢弃：模板节重复时各节内容按出现顺序合并核对；回写记录写在「## 回写记录」节外（节外标题含「回写记录」的节、节外表头含「线」「文件」列的表，80/02 §4）时，其中的记录照样核对路径、计入重叠检查，读取其他进行中变更时同样计入。只报错不读取会让写错位置的记录在重叠检查里看不见，较晚的变更不写依赖也能通过。proposal 的影响矩阵写在「## 文档影响矩阵」节外同样判格式错误，但不核对：矩阵以节内那张表为准，节内只能有一张。
4. **「在本分支有改动」**：`git merge-base <base> HEAD`（`--base` 缺省 `origin/main`，不存在时退到 `main`）之后的提交加工作区改动与未跟踪文件。
5. **棘轮**：G4、G5 各有基线 JSON（`docs/_tools/req-coverage-baseline.json`、`doc-refs-baseline.json`），由 `--write-baseline` 生成，都不含行号：G4 以（需求编号, 线）为键；G5 以（文件, 类别, 引用）为键、记出现次数。新出现的缺口即失败（G5：次数超过基线）；基线里已不存在的缺口也失败（G5：次数减少），提示运行 `--write-baseline` 收紧，保证基线在仓库里只减不增。`--write-baseline` 在解析出错时拒写并退出 1，因为此时算出的缺口与失配不可信、写进基线就成了被放行的缺口：G4 为 PRD 的格式错误或读取问题、各线目录缺失或文档读不了、不是 UTF-8、HTML 注释未闭合、证据清单读不了；G5 为读取问题，即来源文件、归属文档、PRD 或证据清单不是 UTF-8、围栏或注释未闭合，或来源文件、PRD、证据清单读不了（归属文档或基线文件读不了是环境错误，退出 2）。与 `--json` 同用时照样输出机读结果（`baselineWritten: false` 与问题清单）。基线文件不存在时视为空；不是合法 JSON 或条目不合法时报「基线文件:行」、退出 1，`--write-baseline` 照样整体重写（G5 带文件参数时拒写）。写入时较原基线新增的条目逐条列出，须在评审中说明。G5 给出文件参数时只比对、只替换这些文件的键。
6. **G5 与 80/02 §3 的差异**：80/02 §3 写「首批六类引用全部能在归属文档中解析」。现有文档已有失配，直接全量失败会阻断一切文档提交，因此 G5 同样按棘轮执行，直到 `docs-coverage-baseline` 清零。这是实现中发现的文档缺口，按 80/01 §5 回到文档补一句并记偏差。

## Risks / Trade-offs

- [正则误报] → 每个脚本附带验证：对真实文档抽样核对报出的缺口与失配确属真实；误报以收紧规则解决，不靠豁免清单。
- [分支基点不可达，如浅克隆] → 报明确错误（G1–G3 需要 `origin/main` 可达），不静默通过。
