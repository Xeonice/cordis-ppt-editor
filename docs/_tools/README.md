3. **规模**：单图 ≤40 个非空行、≤25 个节点（`flowchart` 不计子图；状态图计状态；时序图计参与方），超了就拆图。既有 3 张超限图（`40-modules/00-module-map.md` 水平层网格图、`15-server-architecture-review.md` §4.2/§4.3 两张模块图）保留不拆（原登记的 `02-kernel-protocol-and-document-core.md` 命令执行管线图已于 2026-09-25 拆为两张，移出豁免），登记在 `mermaid-check.cjs` 顶部的 `EXEMPT` 表（文件 + 登记时起始行 + 首行锚点）；新增豁免须经总编排裁决。
4. **图名、怎么读、依据**：每张图的上一行是加粗图名（如 `**图 5-1 名称**`；带编号时同一文档内按出现顺序编号，见 GV-08 先例）；图后紧跟一段「怎么读：」，说明箭头、虚线、带叉边或分组的含义与阅读顺序；图的内容来自章程条目、裁决或其他文档时，再跟一段「依据：」写明出处。文档站把加粗图名作为图卡标题、「怎么读」收为图注。
5. **必须过校验**：改图后在仓库根目录对改动文件运行 `node docs/_tools/mermaid-check.cjs <文件...>`（全量时传 `docs/` 下全部 `.md`），要求 `0 invalid`。

## 流程门禁（G1–G5）

判定以 `80-process/03` 为准（G4、G5 的覆盖与引用规则见 `80-process/02` §1、§3），本节只记运行方式与三个脚本（及共享模块 `prdlib.py`）的共同约定（rulings §4.25）。`m0-ci-workflows` 接入 CI 之前，agent 在本地运行，把输出摘要写进变更 docs-sync 的「检查结果」；接入后作为 `scanners` job 下的 `process-*` 步骤运行（步骤名见 70/12 §2，本地复现见 70/12 §12）。

```bash
# 每次改文档后（只改 docs/** 的 L0 提交只过 G4、G5、G7）
python3 docs/_tools/check-req-coverage.py                   # G4 需求覆盖，按基线棘轮
python3 docs/_tools/check-doc-refs.py                       # G5 文档引用反查，按基线棘轮
# 进行中的变更，在其分支上
python3 docs/_tools/check-change-impact.py --change <id>    # G1–G3；--gate link|review|impact 只跑一项
# 补上缺口或失配之后收紧基线，随同一提交入库
python3 docs/_tools/check-req-coverage.py --write-baseline
python3 docs/_tools/check-doc-refs.py --write-baseline
```

- **需求编号口径**（只在共享模块 `prdlib.py` 实现，三个脚本共用；条文以 `80-process/02` §1.1、§1.2 为准，改规则先改那里，再改 `prdlib.py`）：需求只在 PRD 03（`10-prd/03-features/*.md`，任一文件可定义九个功能域 `OF`、`ED`、`CO`、`PS`、`EM`、`SV`、`ML`、`AS`、`PM` 中的任一个）与 PRD 04（`10-prd/04-non-functional-requirements.md`，只定义 `NF`）的正文里定义，围栏代码块、HTML 注释与 `> 状态：` 头行不算。定义行只有两种：`#` 顶格的二级或三级标题紧接编号（`### <ID> <标题>`、`## NF-01 …`；一级标题与 `####` 及更深的标题不算），或以 `|` 开头、首格是编号的表格行（功能域须是本文件以标题行定义过的、首格不是区间或列表、该编号未在 PRD 任何地方以标题行定义；不满足的是引用行，不归入任何需求块，行里写了需求字段报格式错误）；ID 形如 `[A-Z]{2,3}-\d{2}[a-z]?`（如 `ED-15a`），字母数字只认半角，其后不能紧跟 ASCII 字母数字。需求块从定义行到下一个需求或级别更高（`#` 更少）的标题之前，表格行定义的遇到任何标题即止；优先级、目标里程碑取块内首个 `优先级：P0|P1|P2`、`目标里程碑：M<n>`（标题行里的不算，表格行定义的取编号之后的单元格），PRD 03 的需求缺任一项或同一字段多于一处报格式错误；落点豁免取块内单独成行的 `- 落点豁免：<线>——<理由>`（线取 设计 / 前端 / 后端 / 前后端 / 测试，理由不能为空或占位，同一条线取第一条）；标题末尾带「（已删除）」括注且块内没有优先级的是已删除需求；同一编号重复定义以首次为准、报格式错误。引用识别：文本中独立出现的编号（前后不是 ASCII 字母数字，所以 `PRD:ED-05`、`PRD ED-05` 照常识别）；`CO` 前缀须带 PRD 字样才算（编号前 15 个字符内有「PRD」、是指向 `10-prd/` 的链接文字或紧跟其路径、或是这类编号的列表续项），前 15 个字符内有「§4.18」「4.18/」或「rulings」的是 rulings §4.18 的条目、不算（带 PRD 也一样）；写在「证据」之后、属于证据清单的编号，以及「能力 id」列与「id | 能力」表首列里的编号不算。G4 另计各线文档围栏代码块里的编号，G5 只查正文；G3 读 proposal「## 需求编号」时只去掉 rulings §4.18 的条目。
- **棘轮**（`80-process/02` §1.3、§3.5）：G4、G5 各有一份基线（`req-coverage-baseline.json`、`doc-refs-baseline.json`），记 `dev-process` 归档时已有的缺口与失配（G4 以「需求编号 × 线」为键，G5 以「文件 × 类别 × 引用」为键、记出现次数，都不含行号）。不在基线里的新条目（G5：次数超过基线）即失败；基线里已经消失的条目（G5：次数减少）也失败，提示运行 `--write-baseline` 收紧，使基线在仓库里只减不增。`--write-baseline` 在解析出错时拒写、退出码 1（G4：PRD、各线文档或证据清单有解析错误；G5：有读取问题），因为此时算出的缺口与失配不可信，与 `--json` 同用时照样输出机读结果。基线文件不存在时视为空；不是合法 JSON 或条目不合法时报「基线文件:行」、退出码 1，不带文件参数的 `--write-baseline` 可整体重写。基线不手改，也不得用 `--write-baseline` 把新缺口放进基线；由变更 `docs-coverage-baseline` 清零。
- **退出码**：0 通过；1 门禁失败（含格式错误、读取问题、基线不合法与可收紧条目）；2 环境或用法错误。G1–G3 的 2：不是 git 仓库、基点不存在、求不出 merge-base、参数错误、内部错误；G5 的 2：未知选项、文件参数不存在或是目录、docs 根目录不存在、归属文档或基线文件读不了、内部错误。G5 带 `--json` 时照样输出含 `error` 字段的 JSON，G1–G3 除参数错误外同样如此。G4 没有退出码 2：目录或文件缺失、读不了都按错误报出、退出码 1，未知参数也退出 1。
- **G6**（代码标识符登记 `check-doc-registry.py`、源文件与 40-modules 目录树 `check-module-tree.py`）与 lefthook 的 pre-commit / pre-push 挂法随变更 `m0-governance-gates` 落地（`80-process/03` §1、§5），届时登记进上表。

## 说明

- 文档站发布为 claude.ai artifact；链接是账号级的，换机器登录同一账号即可访问与更新。
- 这些脚本都只读仓库内容；会写回的只有 `validate-module.py`（只展开「同上」简写）与 `check-req-coverage.py`、`check-doc-refs.py` 的 `--write-baseline`（只写各自的基线文件）。
- **改文档后必跑**（rulings §4.20 TX-02、TX-04；2026-10-01 加第三条；2026-10-04 加 G4、G5）：`python3 docs/_tools/check-links.py`、`python3 docs/_tools/check-terms.py` 与 `python3 docs/_tools/check-plugin-counts.py`，要求都是 0 失配 / 0 残留（退出码 0）；`python3 docs/_tools/check-req-coverage.py` 与 `python3 docs/_tools/check-doc-refs.py` 按基线棘轮通过（退出码 0，见上文「流程门禁」）；改了图另跑 `mermaid-check.cjs`，改了 `40-modules/01–13` 另跑 `validate-module.py`，改了 60-backend 的 SQL 围栏另跑 `ddl-check.sh`。

- `ddl-check.sh` 会在目标容器里 `DROP DATABASE IF EXISTS <库名> WITH (FORCE)`：复用容器时不要把 `CORDEX_DDL_DB` 指向有用的库。改了 60-backend 的任何 SQL 围栏都要重跑它，要求末行输出「通过」。
